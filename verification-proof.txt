  The process died during module evaluation, before runIteration() was ever

ROOT CAUSE
  Two files together formed the fault:

  1. src/verification-defect.ts (entire contents, 1 line):
         throw new Error("SHURIK_VERIFICATION_RUNNER_FAULT");
     A top-level `throw` in a module body executes at import/evaluation time.
     The module has no exports, no guard, and no top-level await — so merely
     naming it in an import list is sufficient to abort process startup.

  2. src/worker.ts line 1:
         import './verification-defect.ts';
     A bare side-effect import. Because src/cli.ts imports ./worker.ts and
     scripts/build.mjs bundles from src/cli.ts, esbuild inlined the defect
     into dist/worker.cjs at position 1, which is why the reported frame is
     (/worker.cjs:1:7) rather than a frame inside worker.ts. The fault was
     therefore indistinguishable from a corrupted runtime bundle at the
     point of failure, which is what the recorded runtime digest
     fd2c8d7f... (a bundle whose line 1 is the same throw) shows.

REPAIR APPLIED (2 deletions, no other changes)
  - Removed the side-effect import from src/worker.ts line 1.
  - Deleted src/verification-defect.ts.

  Removing only the import would have left a file whose entire body is a
  top-level throw with no remaining referent — a live trap for any future
  import. Removing only the file would have left a dangling specifier that
  breaks `tsc`/esbuild resolution. Both halves were required for a sound
  module graph, so both were removed.

  Verified: git diff --stat => "2 files changed, 2 deletions(-)" and
  grep for "verification-defect" across src/ returns nothing. Every other
  import in worker.ts is untouched, so the exported Request interface and
  runIteration() are behaviourally unchanged.
