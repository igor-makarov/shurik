## Retrieval and error handling

Use source/capture evidence to explore eligible image URLs, sizes, extensions, CDN hosts, filename-prefix CDX queries, other capture timestamps, and archived permalink, listing, tag, month, AMP or photoset pages. Confirm that recovered images belong to the target post. Scope shared-CDN queries to known media identities; an incomplete host dump is not a complete inventory. Avoid repetitive successful examples except as bounded health controls. Preserve candidate coverage and fair access to untried and incomplete work.

Classify errors by what was actually observed:
- Connection refusal, DNS/TLS failure, timeout, malformed responses, 504 and absent HTTP responses are transient or inconclusive transport/service failures. HTTP status 000 means no HTTP answer. Do not convert these into archive_gap, an empty CDX result, or proof of throttling.
- A genuine 429 or 503, explicit rate-limit response or Retry-After supports throttling/backoff. Honor that evidence. Keep transport retry policy separate from rate-limit policy; connection refusals alone do not prove a rate limit.
- A successful empty CDX response is negative evidence only for its exact URL/prefix, filters, date range and query scope. A replay 404 applies to that specific capture/URL; alternate eligible captures and variants may remain. Do not generalize partial or failed searches to the whole archive.
- A local circuit breaker or cooldown that skips a request is a deferral, not a network attempt or remote response. Record whether a request was actually sent. Do not inflate attempt counts or benchmark speed using requests the client short-circuited.
- An archived HTML error body is not an image even if the request returned 200. Validate file signatures and verify the actual capture timestamp through redirects. Reject live-site fallback and captures after 20191231235959; retain the reason without declaring all other captures unavailable.

Use bounded retries, timeouts and backoff appropriate to the observed error, with a saved retry eligibility/cursor. Avoid repeating identical failed requests within a run without new evidence. Choose whether another candidate, method, transport or later retry offers better expected progress. Test current HTTP/HTTPS archive behavior rather than trusting stale notes: previous runners sometimes reached HTTP replay while HTTPS refused. A single known-good capture can help distinguish transport failure from candidate-specific failure. Keep network stages coordinated with modest load. When a network path becomes unproductive, checkpoint its evidence and continue useful diagnosis, repairs, offline validation or another promising path while respecting backoff.

Programming errors and failing offline tests are code defects, not archive evidence. Preserve the reproducible command and error, make the smallest useful fix, and verify the behavior you changed with dummy credentials and mocked transport. Retry the affected real path when useful. Do not erase earlier attempt evidence or spend a whole continuation repeatedly rediscovering the same defect.

Preserve successful response bytes, their source/capture identity and hash promptly in task-owned storage that can survive the next runner. A temporary in-memory probe or /tmp file is not durable progress. Keep this state in the registry persistence scheme described above; do not add bulk image bytes to Git. Provider errors, interrupted tools and iteration timeouts likewise require recoverable partial state and an honest saved outcome.
