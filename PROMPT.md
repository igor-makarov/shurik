This is a fresh Shurik experiment branched from main. Implement the downloader, discover the files, retrieve them, and publish the artifacts from inside this Shurik loop. Do not read, copy, merge, cherry-pick, or reuse any falafel task branch, code, artifacts, or task history. ## Slow origin, dropped connections, and durable resume

The origin is slow and drops connections. Resume and speed throttling are core acceptance criteria, not optional polish.

- Use one active origin download initially, an explicit configurable bandwidth limit starting around 256 KiB/s, and a 2-second or longer gap between origin requests. Preserve origin cooldown/backoff state across iterations. If reliable progress warrants increasing the limit, stay conservative (at most 512 KiB/s initially) and document the evidence. Avoid parallel HEAD/GET bursts and retry storms. Honor Retry-After and back off with jitter on connection drops, stalls, 429, and transient 5xx; reduce speed after repeated failures. Retry the remaining work in later bounded passes instead of exhausting the run on one URL.
- Use bounded connection/read/overall timeouts that tolerate a slow transfer. Run foreground tools in short, bounded batches so the supervisor can publish at tool-round boundaries. A practical bound is roughly 60-120 seconds per transfer batch followed by saving durable state. Do not leave detached writers running across checkpoints or rely on an uncheckpointed background job.
- Retain partial bytes after errors and resume by HTTP Range with correct byte offsets and available ETag/Last-Modified validators (If-Range). Verify 206 Content-Range before appending. If the server ignores Range and returns 200, never append a full restart response to an existing partial. Handle changed validators, incorrect ranges, 416, redirects, stalled bodies, interrupted writes, and a server without Content-Length honestly. Preserve valid prior chunks when possible, and replace invalid state safely rather than silently corrupting a file.
- Resume must survive a FRESH Actions runner, not merely restarting a process on the same disk. Use the configured ignored checkpoint paths `data/nauka/state` and `data/nauka/partials` for durable task metadata and selected partial bytes on the CONTROL branch. Shurik restores absent files from these paths before each worker. Keep metadata and chunks consistent, write state atomically, verify restored chunk lengths/hashes, and recover sensibly from a torn or stale snapshot. Keep individual checkpoint files/chunks comfortably below GitHub's file limit (for example at most 16-32 MiB); use GHCR checkpoint artifacts for larger state rather than growing unbounded Git history. Never place an unbounded monolithic partial in a control checkpoint. Save partials frequently enough that normal iteration transitions preserve meaningful download progress.
- Completed bytes must move to GHCR as soon as practical. Persist the published digest and manifest before removing local data. On a new iteration, skip only artifacts proven complete; recover unpublished complete downloads and partials, and never restart already verified artifacts from zero. Existing GHCR artifacts and any resume index should be read and validated before uploading replacements. Do not delete or overwrite a verified completed artifact during recovery.
- Verify the implementation with a small local HTTP fixture that intentionally drops a transfer, honors Range, ignores Range, and changes a validator. Include a cold restart/resume check that reconstructs progress from the chosen durable storage. Fix demonstrated defects before continuing the bulk retrieval. These checks and the actual downloads must be done by this worker, not outsourced to the launching assistant.

## Branch hygiene and persistence

No large data files in the LOOP/work branch, including earlier commits. Only small task code, tests, configuration, manifests, and status/documentation belong there. Ignore `data/nauka/`, staging files, scan formats, downloaded archives, OCI blobs/layouts, and logs BEFORE creating them. Do not force-add ignored data. Audit staged blob sizes before committing. Completed scans belong in GHCR; selected ignored state/partial chunks may be snapshotted onto the separate control branch through `checkpointPaths`. Keep large generated bytes outside tracked task paths and avoid printing binary or base64 content into public transcripts.

Use the coding tool's initial task checkout for all task changes; `GITHUB_WORKSPACE` is a separate supervisor checkout. Never change the supervisor checkout, control bookkeeping, Actions workflows, or stop/resume settings. Preserve checkpoints and continue useful work after ordinary progress saves. Diagnose and repair blockers while respecting the origin's backoff. A temporary source failure is not task completion. A final task response is appropriate only after all scoped scans and the collection index are retrieved, published, and verified; otherwise leave evidence and keep working within the supervisor's budget.
